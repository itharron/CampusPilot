一、项目概述

1.1 项目定位

CampusPilot 是一个面向高校学生的校园办事服务台原型。学生不需要事先知道事情归哪个部门管，也不需要在几十页学生手册里翻条款， 只要用日常语言说一句「宿舍空调坏了」「我要开在读证明」，系统就会给出去哪个部门、走什么流程、带什么材料、注意什么， 并在回答下方附上学生手册的原文出处，点击即可核对。

项目当前版本为 v0.2.0，定位是「一位真实学生能用、换一所学校只改数据」的可演示作品。语料是按真实学生手册体例自编的示例， 但检索、引用、上传入库、鉴权、流式输出、限流与额度控制全部是真实实现，不是静态页面或写死的问答对。

1.2 要解决的问题

痛点具体表现CampusPilot 的应对
不知道找谁 空调报修、证明开具、缓考申请分属后勤、教务、考试中心，学生靠问同学或群聊打听。 用自然语言识别事项，直接给出归属部门与办理入口。
手册难查 手册按章、条组织，关键词与口语不一致；搜「空调」未必能命中「学生社区与后勤」。 中文单字 + 双字检索，标题加权，按小节切块后召回。
回答不可信 通用大模型容易编造部门、电话、时限，学生无法核实。 只依据检索到的片段回答，强制用 [n] 标注，前端可展开原文。
成本与滥用 公开演示时接口可能被脚本刷取，模型调用是唯一有成本的环节。 输入过滤、按 IP 限流、每日请求与 token 额度、答案缓存。
换校成本高 多数校园问答 Demo 把学校名、部门、流程写死在代码里。 学校配置与语料全部外置，提供三种换校方式。

1.3 当前形态与真实规模

产品形态

  • 单页对话界面，首次进入有使用引导与 9 个示例问题。
  • 回答逐字流式出现，末尾附「依据来源」，可展开手册原文。
  • 「知识库入库」页需登录，支持 PDF / Word / Markdown / TXT 上传、切分预览与确认入库。
  • 桌面端与移动端共用一套页面，窄屏单列布局。

真实运行数据

  • 知识库：11 篇文档、34 个片段、3413 字。
  • 内置 10 个办事事项：报修、校园卡、校园网、教室借用、在读证明、缓考补考、休学复学、请假、奖学金、违纪申诉。
  • 1 篇运行期上传文档「图书馆研讨间预约」，4 个片段，已参与检索。
  • 检索方式：BM25（未配置向量模型时的默认实现）。
关于「示例大学」：语料中的学校名、部门、电话均为示例数据，不对应任何真实学校。这样既能完整演示手册体例， 又避免把未经授权的真实校内信息放进公开仓库。换校方式见 4.7 节。

1.4 设计原则

第一版遵循五条原则：先可信，再智能——回答必须落到具体文档、章节、条款，检索不到就明确说未收录； 没有 Key 也能完整演示——mock 与 live 共用同一条检索、引用与流式链路； 数据与代码分离——学校信息、部门、语料都在 config/ 与 data/，代码中没有学校专属硬编码； 成本可控——模型调用都在服务端，入口处先做过滤、限流、额度与缓存； 移动端不是缩小版——窄屏重新排版，处理软键盘遮挡，触屏回车只换行。

二、需求分析

2.1 用户角色与场景

角色典型场景核心诉求
在校学生 宿舍空调漏水；校园卡丢失；需要开在读证明；对处分有异议。 一句话说清要办的事，马上知道部门、入口、材料与时限，并能核对依据。
新生与家长 不熟悉学校部门划分，不知道「教务处」和「学生工作处」分别管什么。 不需要懂组织架构，用生活语言描述问题即可。
辅导员 / 服务大厅 重复回答相同问题，需要快速给出标准口径。 回答与手册一致，有出处，可直接转发给学生。
知识库维护者 手册更新、新增事项，希望不改代码就能生效。 上传文档、预览切分、确认入库，立即参与检索。
评审 / 运维 不配置密钥验收；担心公开演示被刷接口。 mock 可演示；有模式标识、限流、额度与错误提示。

2.3 非功能需求

维度约束与实现
可信度只依据检索片段回答；系统提示词禁止编造部门、电话、网址、时限；检索不到时明确说明未收录并给出人工兜底。
响应体验先返回 meta（意图、引用、额度），再流式输出正文；模型服务异常时用本地模板兜底，不让页面空白。
安全密钥只在服务端内存；输入过滤在限流与额度之前执行，被拦截的请求不消耗任何额度；知识库写操作需要登录。
成本20 次/分钟/IP；每日 60 次请求、12 万 token；答案缓存 10 分钟 / 200 条；登录与上传各自限流。
可移植学校信息与语料外置；换校只改 config/school.json 与 data/，或设置 CORPUS_DIR。
可维护检索层通过 Retriever 接口注入；LLM 通过 LLMProvider 策略切换；路由只做流程编排。
兼容性Node ≥ 20.3；现代浏览器；不依赖 UI 框架与本地模型文件。

2.4 需求取舍

第一版刻意不做三件事：不做通用聊天（系统提示词明确拒绝写代码、写作文、闲聊与情感咨询）； 不做 OCR（扫描件 PDF 抽不出文字时返回 422 并提示先 OCR，不静默失败）； 不代替用户提交申请（当前只给指引，工具调用列入后续路线）。这些取舍保证演示范围内每条回答都能落到手册依据上。

3.2 请求处理流水线

对话接口 POST /api/chat 的固定顺序如下，任何一步拒绝都不会进入下一步：

  1. 输入过滤：空输入、超过 500 字、注入 / 越界 / 隐私信息直接返回 400，不消耗额度。
  2. 单 IP 限流：固定窗口 60 秒，上限 20 次；超限返回 429 与 Retry-After。
  3. 每日额度：按 IP 统计当天请求数与 token 估算值；超限返回 429。
  4. 答案缓存：命中则按原引用流式回放，tokens=0，不再检索与调用模型。
  5. 检索与组装：BM25 取 topK=4 → 按文档与「办理步骤」重排 → 生成意图与引用 → 渲染编号参考资料。
  6. 流式生成：调用 Provider 逐段输出；结束后累计 token、写入缓存；异常时用本地模板兜底。

3.3 SSE 事件协议

事件载荷前端行为
meta{ mode, model, intent, topDocTitle, citations[], retrieval, cached, quotaRemaining, rateRemaining }渲染意图、检索方式、引用卡片与剩余额度。
delta{ text }追加到气泡，保持光标，滚动到底部。
done{ cached, tokens }结束流式状态，减少一次剩余额度。
error{ code, message }保留已输出内容，在气泡下展示错误说明。

说明：前端使用 fetch + ReadableStream 自行解析 SSE，因为浏览器原生 EventSource 不支持 POST； 后端关闭代理缓冲（X-Accel-Buffering: no），避免整段内容被一次性下发。

3.6 静态托管与深链接回退

生产构建后，Express 用 express.static 托管 web/dist，前后端同源，不需要额外的 Nginx 静态站点。 前端使用 History 路由，直接访问或刷新 /upload、/chat 这类深链接时，服务端必须回退到 index.html，否则会出现 404。当前实现把这层回退放在静态中间件之后、统一 404 之前： 

GET /upload          → 200，返回 web/dist/index.html
GET /assets/app.js   → 命中则返回文件；文件缺失 → 404
GET /api/nonexistent → 404，JSON {"ok":false,"code":"NOT_FOUND"}

回退只对 GET 生效，并显式排除 /api 前缀、/assets/ 前缀和带扩展名的路径。 这样既保证深链接刷新可用，又不会把缺失的静态资源或 API 错误吞成 HTML 页面。

四、AI 技术方案

本章说明系统「怎么找到依据、怎么组织回答、怎么保证不越界、怎么控制成本」。 所有参数都来自当前代码常量与环境变量默认值，实测值标注了测试时间与问题。

4.1 选型理由

本项目的 AI 能力按「能离线跑、能换供应商、能解释依据、能控制成本」四条约束选型，没有为了技术栈好看而引入 向量数据库、模型微调或前端 UI 框架。关键决策与理由如下：

决策点当前选择选择理由未采用
检索 BM25 为主，可选向量混合（0.65 / 0.35） 校园手册关键词密度高，中文「单字 + 双字」即可覆盖口语问法；当前 34 个片段用内存索引足够，评审机器无需 GPU、无需下载权重。配置 embedding 后自动升级，失败自动退回 BM25。 向量数据库、Elasticsearch：增加部署与运维依赖，对当前语料规模收益有限
生成模型 OpenAI 兼容 HTTP 接口 只依赖 baseURL + model + apiKey，换供应商不改业务代码；SSE 直接透传，前端协议稳定。 绑定单一厂商 SDK：升级与迁移成本高
意图识别 复用检索结果的文档聚合 没有标注数据，训练分类器成本高且冷启动不可用；用「第一名与第二名文档的分差」估置信度，语料内问题稳定在 0.87–0.99。 独立文本分类模型：需要标注集与模型产物
流式传输 SSE 回答是单向增量，SSE 基于普通 HTTP，代理与浏览器兼容性好，断线可由前端重试。 WebSocket：双向能力用不上，反而增加连接管理
无 Key 演示 与 live 同链路的 mock Provider 评审没有 Key 时仍能走通检索、引用、流式与前端交互，避免「演示环境打不开」。 仅 live：无 Key 无法验收
上传鉴权 内存 token + 登录限流 单实例演示规模下零外部依赖，重启即失效，逻辑简单可核对。 JWT + Redis：当前不需要多实例会话
文档解析 multer + pdf-parse / mammoth 同步解析、依赖轻，PDF / DOCX / MD / TXT 覆盖手册常见格式；50 MB 上限足够单份手册。 OCR、对象存储：扫描件与大规模入库不在当前范围

4.2 集成方式

所有 AI 能力收敛在一条固定流水线里，路由层不直接调用模型，也不在页面里拼检索逻辑： 

输入过滤 → 单 IP 限流 → 每日额度 → 答案缓存 → 检索（BM25/混合）
        → 引用与意图 → 组装 Prompt → Provider.stream() → 记账/缓存 → SSE
  • 接口解耦：检索侧统一 Retriever.search(query, options)，模型侧统一 Provider.stream({ messages, fallbackText }, signal)；mock 与 live 只是两个实现，路由代码完全相同。
  • 单例装配：runtime.ts 在启动时加载语料、建立索引、创建 Provider、限流器、额度与缓存， 路由通过导入单例使用，避免每个请求重复构建索引。
  • 引用先行：先由检索片段生成 citations 并通过 SSE meta 事件下发，再开始流式正文； 正文里的 [n] 与引用数组下标一一对应，前端不需要二次匹配。
  • Prompt 契约：系统提示词要求「只依据参考资料、先结论后步骤、不超过 250 字、关键结论标注 [n]、不编造部门与电话」； 参考资料按 [1]…[4] 编号注入，编号与引用列表同源。
  • 失败兜底：模型不可用时，用同一批检索结果调用 composeAnswer() 生成模板答案，仍经 SSE 输出， 前端不需要切换错误页。
  • 上传入环：multer 接收文件 → 解析纯文本 → 按 ## / ### 切块 → 草稿预览 → 确认后写入 data/uploads/，随后重载语料并重建检索索引，新文档立即参与问答。

4.4 意图识别

意图识别不单独训练分类模型，而是复用检索结果：把片段按文档聚合，取最高分文档作为意图； 置信度用「第一名与第二名文档的分差」估算，而不是归一化后的绝对分。这样语料只命中一篇时接近 0.99， 两篇得分接近时回落到 0.55 左右，能如实反映「是否分得清」。 

const runnerUp = groups[1]?.score ?? 0;
const margin = top.score > 0 ? (top.score - runnerUp) / top.score : 0;
const confidence = Number(Math.min(0.99, Math.max(0.4, 0.55 + 0.44 * margin)).toFixed(2));

4.5 中文检索与 BM25

4.5.1 切词

为了不引入分词词典或模型文件，中文按「单字 + 相邻双字」切分。双字覆盖「空调 / 报修 / 学籍 / 教室」这类常见词， 单字兜底召回；英文与数字按整词保留；同时过滤「的、了、我、在」等高频虚词单字，避免无关片段被抬高。 汉字与英文相邻时强制断开，防止「宿舍wifi」被拼成一个词。

4.5.2 BM25 打分

每个片段建立词频表，按标准 BM25 计算：

score = Σ  idf(term) · tf · (k1 + 1) / ( tf + k1 · (1 - b + b · |D| / avgdl) )
idf(term) = ln(1 + (N - df + 0.5) / (df + 0.5))

代码中 K1 = 1.2、B = 0.75。索引文本把事项标题重复三次，再拼章、条、小节与正文， 因此标题命中的权重最高。查询里命中双字（比单字更具体）时，每个双字额外加 0.15 分。 检索结果按最高分归一化到 0–1，前端与意图层拿到的都是归一化分。 

// retrieval/bm25.ts
const indexText = (chunk) => [chunk.docTitle, chunk.docTitle, chunk.docTitle,
  chunk.chapter, chunk.article, chunk.section, chunk.text].filter(Boolean).join('\n');
const specificBoost = matched.filter((term) => term.length > 1).length * 0.15;

实测问题「宿舍空调不制冷了怎么报修，要准备什么材料」在 live 模式下命中 4 个片段，最高归一化得分 1， 命中词为 宿舍、舍空、空调、调不、不制、制冷；mock 模式下问题「宿舍空调漏水该找谁处理」同样命中 4 个片段， 命中词为 宿舍、舍空、空调、漏水、宿、舍。两例都正确落到「宿舍空调报修」文档。

4.5.3 可选向量混合

默认只跑 BM25，不需要任何模型权重。配置 EMBEDDING_MODEL 与 EMBEDDING_API_KEY （可复用 LLM_API_KEY）后，服务端调用 OpenAI 兼容的 /embeddings 接口建立片段向量索引， 查询时按 0.65 × BM25 + 0.35 × 余弦相似度 合并；批量大小为 16，查询向量缓存 100 条。

降级策略：向量接口失败或返回维度异常时，只记录一条状态说明并退回纯 BM25，不影响回答主链路。 /api/health 的 retriever 字段会显示当前是 bm25 还是 hybrid(bm25+vector)， 便于验收时确认实际运行状态。

4.6 引用溯源

引用不是回答生成后再「补来源」，而是从语料加载时就把出处写进每个片段：docId / docTitle / document / chapter / article / section / source / pages / department / excerpt。 回答阶段只做筛选、排序与渲染，因此引用的文档名、章、条、小节与原文天然一致。

片段出处串示例（真实输出）：

《示例大学学生手册（2026）》 · 第八章 学生社区与后勤 · 第五十条 · 办理步骤

排序规则：orderHitsForAnswer() 先按文档最高分排序，同一文档内按小节优先级重排： 办理步骤 → 材料/证件 → 适用/条件 → 注意/说明。这样 [1] 永远是最关键的流程片段，而不是「恰好命中次数最多」的小节。

回答约束：系统提示词要求「只依据参考资料回答」「每个关键结论后用 [1]、[2] 标注，编号必须与参考资料一致」。 引用列表默认取前 3 条，前端展示 source，展开后展示 excerpt（片段正文，超过 600 字截断）。 mock 模式与模型失败兜底时，模板答案末尾会自动附「依据来源」，格式与 live 模式一致。

6.6 已知限制

  1. 语料是自编示例（10 条事项 + 1 条上传），替换为真实手册前，回答只能覆盖这 11 篇文档。
  2. PDF 抽文本依赖文本层，不做 OCR；扫描件会明确报错。
  3. 向量检索默认关闭，未做 rerank；BM25 对同义改写（如「制冷不行」与「不制冷」）仍可能漏召回。
  4. 限流、额度、会话、预览草稿均为进程内存储，重启清零；多实例部署需换 Redis 与共享存储。
  5. 输入过滤是规则实现，存在漏拦与误拦；越界请求仍可能以正常问答形式出现。
  6. 尚未接入真实办事系统，不能代替用户提交申请或查询进度；上传写入本地 data/uploads/，适合单实例演示，不适合多租户并发写入。

七、创新点

下面按赛道要求拆成两类：技术创新点回答「工程与算法上做了什么别人没做的处理」， 应用创新点回答「这些处理如何改变校园场景里的实际使用方式」。每一条都能在代码或实测数据中找到对应。

7.1 技术创新点

7.1.1 回答与手册逐条对应，而不是「看起来像」

多数校园问答 Demo 只保证「答得像」，CampusPilot 把出处信息前置到语料加载阶段：每个片段天然带有文档名、章、条、小节和原文， 回答阶段不生成出处，只排序与渲染。因此引用可以展开、可以核对，回答里的 [1] 与展开的原文严格对应。 排序上再把「办理步骤」提到同文档首位，让第一条引用就是学生最需要的流程，而不是机械按得分排列。

7.1.2 零模型文件的中文检索也能可用

不下载分词词典、不加载 embedding 权重，仅靠「单字 + 相邻双字」与标题三倍加权，就能把「宿舍空调漏水」正确落到 「宿舍空调报修」文档。对比赛场景很实际：评审机器无需 GPU、无需联网下载模型，克隆后装依赖即可跑。 需要更强召回时，配置 embedding 即升级为混合检索，失败自动退回 BM25。

7.1.3 mock 与 live 共用一条链路

mock 不是「假页面」，而是同一检索、同一引用、同一模板答案、同一 SSE 协议下的另一种输出实现。 这让「没有 Key 的评审」和「有 Key 的验收」看到完全一致的产品行为，也让模型故障时的兜底成为自然结果，而不是额外分支。

7.1.4 成本护栏做在入口，而不是事后统计

输入过滤 → 限流 → 每日额度 → 缓存 → 检索 → 模型调用是固定顺序，前四步任何一步拒绝都不会产生模型费用； 缓存按归一化问题命中并回放引用，实测把 9.99 秒、126 tokens 的请求降为 684 毫秒、0 token。

7.2 应用创新点

7.2.1 换学校是数据操作，不是开发任务

学校名、学期、部门、入口在 config/school.json，事项在 data/，语料通过 frontmatter 的 departmentKey 关联部门；代码中没有「示例大学」或具体部门名的硬编码。换校可以改数据、运行时上传， 或直接挂载新的 CORPUS_DIR，三种方式覆盖部署、增量和演示。

7.2.2 移动端按真实使用方式处理

不是把桌面布局缩小：窄屏单列、示例换行、触屏回车只换行、发送只走按钮、用 visualViewport 跟随软键盘收缩外壳高度。 这些细节直接决定「学生在宿舍用手机问一句」是否能顺利完成。

八、总结与展望

8.1 已完成

  • 从「一句话提问」到「带出处回答」的完整闭环：中文检索、意图识别、引用排序、流式输出、前端展开原文。
  • 可扩展知识库：登录鉴权、PDF / Word / Markdown / TXT 上传（单文件 50 MB）、预览切分、确认入库、即时重建索引。
  • 可演示的双模式：无 Key 自动 mock，有 Key 走 OpenAI 兼容模型；失败有模板兜底。
  • 可验收的安全与成本控制：四类输入拦截、IP 限流、每日请求与 token 额度、答案缓存、上传与登录限流。
  • 可迁移的数据结构：学校配置与语料外置，三种换校方式，代码零硬编码。
  • 桌面与移动端适配，含首次使用引导、示例入口、登录与上传界面；Express 静态托管 + SPA 深链接回退，刷新 /chat、/upload 不再 404。
  • 可在线验收：阿里云 ECS + pm2 公网部署（http://47.96.20.128:8787），单端口同时提供 API 与前端产物。
